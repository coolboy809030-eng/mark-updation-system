EXECUTIVE SUMMARY
-----------------
A deep architectural and dependency audit was performed on the existing web application
and its companion Google Apps Script backend (`apps-script/Code.gs`).

CRITICAL CORE FINDINGS:
1. THE LOCALSTORAGE TRAP:
   All Teacher Accounts, Teacher Allotments (Class/Section/Subject), Master Subject
   Curriculum, Admin PIN, Segment Locks, and System Controls (Marks Entry Status,
   Deadlines, Working Days) are saved solely in browser `localStorage`.
   Zero institutional configuration is stored in Google Sheets or Google Apps Script.

2. CROSS-DEVICE PERSISTENCE FAILURE:
   When an Admin creates a Teacher ID and assigns them to Class 5-A Hindi on Device A,
   it is stored only in Device A's `localStorage`. When the teacher opens the portal link
   on Device B (mobile or laptop), Device B's `localStorage` is completely empty.
   Result: The teacher sees "No Authorized Classes" or is locked out from entering marks.

3. DISCONNECTED TEACHER LINK GENERATION:
   The Teacher Link Hub generates a generic URL (`?portal=teacher`) rather than a
   personalized link with a teacher token (e.g., `?portal=teacher&teacherId=TCH-2026-001`).
   Even if the link included the ID, Device B lacks the account and allotment registry.

4. GHOST BACKEND API CALLS:
   The frontend queries `?action=getSystemControl` to check system status, but `Code.gs`
   contains no handler for this action. It falls through to a generic ping response,
   failing to sync any locks, deadlines, or working days.

5. DUAL SUBJECT ASSIGNMENT PARADIGMS:
   Two competing modules exist:
   - Module A: SettingsModal.tsx ('teachers' & 'admit_card' tabs) -> Teacher Allotment
   - Module B: ClassSubjectAllotmentModal.tsx -> Class Curriculum Master
   They use different storage keys and lack a single source of truth.

PART 3: DUAL SUBJECT ASSIGNMENT MODULES (OVERLAP & CONFLICT)
--------------------------------------------------------------------------------
MODULE A: Teacher Allotment & Permissions
- File: `src/components/SettingsModal.tsx` (Tab: 'teachers')
- Target: Human permissions (Teacher -> Class/Section/Subject)
- State: `teacherAllotments` in `App.tsx` (line 448)
- Storage: `localStorage['pis_teacher_allotments_v1']`
- Backend API: None (zero network calls)

MODULE B: Class Curriculum Master
- File: `src/components/result/ClassSubjectAllotmentModal.tsx`
- Target: Academic syllabus (Class -> Subjects evaluated)
- State: `subjectAllotments` in `App.tsx` (line 264)
- Storage: `localStorage['pis_class_subject_allotments_v1']`
- Backend API: None (zero network calls)

How they interact in Teacher Portal (`App.tsx` lines 706-722):
`authorizedSubjects = teacherSubs.filter(sub => masterSubs.includes(sub));`
They do not overwrite each other directly, but they form a fragile two-stage filter.
If Module B is updated on Device A, Device B still has old defaults, causing
mismatched subject lists for the same teacher.
REDUNDANT DUPLICATE IDENTIFIED:
The sub-tab "Admit Card Subject Allotment" inside `SettingsModal.tsx` is an inferior,
redundant duplicate of Module B (`ClassSubjectAllotmentModal.tsx`).

PART 5: ROLE & SECURITY ARCHITECTURE AUDIT
--------------------------------------------------------------------------------
- Admin Authentication:
  Purely client-side check against `adminPin` (stored in `localStorage['pis_admin_pin_v1']`,
  default '1234'). Active session kept in `sessionStorage['pis_admin_session_active']`.
- Teacher Authentication:
  Purely client-side string match of `selectedTeacherId` against `teacherAccounts`.
  No passwords, tokens, or PINs exist for teachers.
- Server Verification:
  ZERO SERVER VERIFICATION. In `apps-script/Code.gs`, `handleSaveMarks` accepts any
  payload and writes directly to cells without verifying teacher identity or permissions.
- Direct Route Protection:
  Any client issuing an HTTP POST to the Web App URL can overwrite marks without authentication.

PART 6: MIGRATION STATUS & ROOT CAUSE EVALUATION
--------------------------------------------------------------------------------
VERDICT: EXISTING BUG (Pre-existing Architectural Limitation).
Evidence:
- The reliance on browser `localStorage` for institutional multi-user data was authored
  in the original upstream repository (`coolboy809030-eng/mark-updation-system`).
- `Code.gs` never contained endpoints for teacher management or system control.
- Google AI Studio migration cleanly preserved all functionality, builds, and logic.

PART 8: MINIMAL ARCHITECTURE-PRESERVING RESOLUTION STRATEGY
--------------------------------------------------------------------------------
Step 1: Google Sheet Backend Extension (`apps-script/Code.gs`)
- Create `_CONFIG` and `_TEACHERS` tabs in `createPeaceSchoolWorkbook()`.
- Add `doGet?action=getSchoolConfig` returning:
  `{ systemConfig, subjectAllotments, teacherAccounts, teacherAllotments }`.
- Add `doPost` handlers:
  - `action: "saveSchoolConfig"` (writes locks, deadlines, working days)
  - `action: "saveTeacherRegistry"` (writes teacher IDs, accounts, and allotments)

Step 2: Frontend Boot Hydration (`src/App.tsx`)
- On application boot, call `getSchoolConfig`.
- Hydrate React states in memory; retain `localStorage` solely as offline cache.

Step 3: Personalized Teacher Links (`TeacherLinkSyncHubModal.tsx`)
- Generate parameterized links: `${baseUrl}?portal=teacher&teacherId=${teacherId}`.
- Auto-selects the teacher and loads their pre-allotted classes and subjects seamlessly.

Step 4: UI Cleanliness (`Header.tsx`)
- Hide "Download .txt Report" and Result Portal switch buttons when `portal=teacher`.
